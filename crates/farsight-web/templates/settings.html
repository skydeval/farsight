config.toml

Secrets are shown as <redacted> and kept unless replaced. Access, auth, proxy, rate-limit (except the query concurrency) and backfill keys apply immediately; others need a restart. Writes are atomic and notify the backfill process.

The admin UI itself is switched with access.admin_ui in config.toml, at restart; a save here that would change it is refused.

A save that changes auth.*, net.*, backfill.plc_url or backfill.relay_url, or that opens access.reads, access.cors or access.public_ui further, is made only within ten minutes of signing in. Later than that, the save is not stored: you sign in again and make the change once more.

Public UI

A public lookup site at this hostname's root (/): anyone can see who blocks an account, directly and through lists. Removed records are never shown there; they are on the history pages reached from the DID and list lookups, after login. Every setting here applies on save, without a restart; a cache in front of Farsight keeps serving its copies for up to a minute. Open the public UI in a new tab ↗{% if !p.enabled %} (it answers 404 while switched off){% endif %}.

Resting the pointer on an account opens a card with its handle, DID and creation date. With this on, the card also has the account's picture, and the visitor's browser fetches it from the account's own server, whose operator then sees the visitor's address and the time. On a page listing who blocks an account, a blocker who runs their own server can log who looks. Off: cards keep everything else, and visitors' browsers contact only this instance. Cards already cached keep or lack the image for up to five minutes.
Off: a visitor's browser fetches each avatar, and a list's image, as the original upload from the account's own server, about 300 kB each on average. On: it fetches a thumbnail of a few kB from cdn.bsky.app, which browsers keep for a week, so cards and headers load faster. Bluesky's image service then sees the visitor's address, not each account's server, and an image appears only if that service has it. Farsight stores which image an account uses (its CID, read again after a day), never the image. Only with avatars on.
Each card makes this instance fetch from the PLC directory and from the account's server (at most three requests). These requests are not counted in backfill.plc_rps; lower either if your PLC source has a tight limit. With the budget used up, cards show the DID only. A burst below the rate is raised to it. Cards on the admin pages draw on the same budget.
A background worker verifies the handle of every account a page is about to show and has not seen before. A public table leaves such an account out, says how many it left out, and adds them in place as they are verified, so a row is never shown with a handle Farsight has not checked; an account whose check finds no handle is shown as its DID. Admin tables show the DID meanwhile. Applies also with the public UI off. Off: nothing is held back, accounts not seen before show as DIDs, handles appear only as cards are opened and account pages are visited, and a stored handle is never checked again.
How many accounts' handles Farsight verifies per second, for pages, cards and the background worker together. Each check is up to two requests: the account's DID document, then the handle on its own host. At 20 a page of 50 accounts nobody has seen is complete in about three seconds. Lower it if those hosts start refusing requests.
0 = off. Above 0, Farsight works through every account it holds in the background and checks its handle, so that a page's rows have their handles before anyone opens it; accounts whose identity changes on the network are checked first. This is separate from the rate above and runs around the clock: at 10 a second, ten million accounts take about twelve days, and each check is up to two requests to servers Farsight does not run. It waits by itself when most checks fail.
